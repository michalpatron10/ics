# ADR-0006: Identifiers: UUIDv7 internally, per-tenant human claim numbers

Status: accepted

## Context

Each tenant has its own database (ADR-0001). With database sequences as primary keys (today `claim_sequence`), the same ID exists in every tenant: "claim 42" is ambiguous in logs, events, integrations, support tickets and any future data consolidation. Claim handlers and claimants also need a short, readable reference, and insurers often have a prescribed format for it.

## Decision

**Internal identity: UUIDv7 for every aggregate** (claims, documents, communications, etc.).

- Generated by the application, not the database, so the ID is known before the insert (useful for events, idempotency and the Operaton business key). Use Hibernate's `@UuidGenerator(style = UuidGenerator.Style.VERSION_7)` (available in Hibernate 7.4, which Spring Boot 4.1 manages), with no extra library needed. For IDs needed before persisting, e.g. in events, call the same strategy or assign the UUID in the aggregate's factory.
- Stored as PostgreSQL `uuid`. Version 7 is time-ordered, so B-tree index locality stays close to that of a sequence.
- Used in REST paths (`/claims/{id}`), events, logs, integrations and as the Operaton **business key** of the claim process.
- IDs are globally unique, but anything leaving a request context (events, logs, external messages) still carries the `tenantId` too, because the ID alone does not tell you which database to look in.

**Human reference: a claim number, unique per tenant.**

- Assigned once when the claim is registered and never changed. Stored in `CLAIM_NUMBER` with a unique constraint.
- The format is tenant configuration, e.g. `{prefix}-{yyyy}-{seq:6}` → `ACME-2026-000123`. The default pattern applies until a tenant overrides it.
- The sequence part comes from a per-tenant database sequence (optionally reset per year). **Gaps are allowed**: gapless numbering would need serialized locking, and no requirement for it has been raised.
- Used only for display, search (`GET /claims?number=...`) and communication with claimants. It is never used as a foreign key or a reference between systems.

## Consequences

- No ambiguity across tenants, and records can later be merged or exported without re-keying.
- The `CLAIM` table needs a migration from the `BIGINT` sequence ID to `uuid`, and `ClaimDto`/`ClaimsController` switch from `Long` to `UUID`. There is no production data yet, so this is a schema change rather than a data migration.
- UUIDs are less readable in URLs and logs. The claim number covers the human-facing use.
- A tenant that later demands gapless numbering needs a separate decision (a counter table with row locking).
